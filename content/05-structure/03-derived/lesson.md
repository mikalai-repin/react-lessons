Покупателю мало поиска: он хочет видеть только то, что есть в наличии, и сортировать по цене. Добавим флажок и список «Порядок». Но сначала — вопрос, на котором ошибаются чаще всего: где хранить **отфильтрованный список**?

## Соблазн: список в состоянии

Первая мысль — завести состояние для того, что на экране, и обновлять его в обработчиках:

```tsx
const [shown, setShown] = useState(games);
…
onChange={(e) => {
  setQuery(e.target.value);
  setShown(
    games.filter((game) =>
      game.title.toLowerCase().includes(
        e.target.value.toLowerCase(),
      ),
    ),
  );
}}
```

Так список можно получить, но теперь у каталога два источника истины: фильтры (`query`, `category`) и `shown`. Их нужно держать согласованными **вручную**, в каждом обработчике каждого поля. Забыли одно место — они разошлись. Проверим это в эксперименте в конце шага.

## Правило: минимальное состояние

В состоянии храните только то, что **нельзя вычислить** из props и другого состояния. Всё остальное считайте при рендере, прямо в теле компонента.

Пользователь выбирает фильтры — это нельзя вычислить, это состояние. Список на экране — функция от фильтров и каталога. Это **производное значение** (derived value): `const`, а не `useState`. Компонент всё равно вызывается при каждом изменении состояния, поэтому производное значение всегда свежее и никогда не расходится с источником.

Этим правилом магазин уже пользуется: `cartCount` в `App`, итог в мини-корзине, `hits` и `visibleGames` вычисляются при рендере.

## Наличие и порядок

Для сортировки нужна функция сравнения на каждый вариант порядка. Объект `Record<SortOrder, Compare>` гарантирует, что ни один вариант не забыт: уберите любой ключ — TypeScript подчеркнёт объект.

```tsx App.tsx {4-12,16,20-22,24-31}
// Фильтр по категории: одна из категорий или все сразу
type CategoryFilter = Game['category'] | 'all';

// Порядок каталога и функция сравнения игр для каждого
type SortOrder = 'default' | 'cheap' | 'expensive' | 'rating';
type Compare = (a: Game, b: Game) => number;
const COMPARE: Record<SortOrder, Compare> = {
  default: () => 0,
  cheap: (a, b) => a.price - b.price,
  expensive: (a, b) => b.price - a.price,
  rating: (a, b) => b.rating - a.rating,
};

export function App() {
  const hits = games.filter(isHit);
  // Поиск, категория, наличие и порядок — что выбрал покупатель
  const [query, setQuery] = useState('');
  const [category, setCategory] =
    useState<CategoryFilter>('all');
  const [inStockOnly, setInStockOnly] = useState(false);
  const [sort, setSort] = useState<SortOrder>('default');
  // Что показать — вычисляем из состояния при каждом рендере
  const search = query.trim().toLowerCase();
  const visibleGames = games
    .filter(
      (game) =>
        game.title.toLowerCase().includes(search) &&
        (category === 'all' || game.category === category) &&
        (!inStockOnly || game.inStock > 0),
    )
    .toSorted(COMPARE[sort]);
```

- `toSorted` (ES2023) возвращает **новый** отсортированный массив. Обычный `sort` сортирует массив на месте: после `filter` массив и так новый, но привычка `toSorted` защищает от `games.sort(…)`, который переставил бы общий массив каталога — тот же урок, что с мутацией в главе 4.
- «Как в каталоге» — сравнение, которое всегда возвращает `0`. Сортировка в JavaScript устойчивая: равные элементы сохраняют исходный порядок.

Два новых поля — после категории, в той же панели:

```tsx App.tsx
            <label className={styles.field}>
              Порядок
              <select
                className="search"
                value={sort}
                onChange={(e) =>
                  setSort(e.target.value as SortOrder)
                }
              >
                <option value="default">Как в каталоге</option>
                <option value="cheap">Сначала дешёвые</option>
                <option value="expensive">
                  Сначала дорогие
                </option>
                <option value="rating">По рейтингу</option>
              </select>
            </label>
            <label className={styles.check}>
              <input
                type="checkbox"
                checked={inStockOnly}
                onChange={(e) =>
                  setInStockOnly(e.target.checked)
                }
              />
              Только в наличии
            </label>
```

У флажка вместо `value` — `checked`, а новое значение — `e.target.checked` (`boolean`). `e.target.value` у флажка — строка `'on'`, она здесь бесполезна.

::: task

2. Добавьте в `App` состояния `inStockOnly` (`false`) и `sort` (`'default'`). В `visibleGames` учтите наличие (`game.inStock > 0`) и отсортируйте результат через `toSorted`.
3. В панель добавьте управляемый список «Порядок» с четырьмя пунктами и управляемый флажок «Только в наличии» (`<label className={styles.check}>`). Стили новых полей уже в `App.module.css`.
:::

## Что получилось

Выберите «Сначала дешёвые»: «Драконья почта», «Космические коты», «Остров сокровищ», «Маяк», «Нарды», «Ночной экспресс». Отметьте «Только в наличии» — «Маяк» исчез. «По рейтингу» — первым «Ночной экспресс» (4,8). Верните «Как в каталоге» — исходный порядок: `toSorted` не тронул массив `games`. Все четыре фильтра работают вместе, в любом порядке нажатий, потому что список каждый раз вычисляется из всех четырёх.

## Эксперимент: список в состоянии

Сделайте так, как в начале шага. Добавьте после `sort` состояние `const [shown, setShown] = useState(games);`, в сетке «Всех игр» рисуйте `shown.map(…)` вместо `visibleGames.map(…)`, а в `onChange` поиска обновляйте и `query`, и `shown` — код из первого раздела.

Редактор сразу заметит лишнее: `'visibleGames' is declared but its value is never read.` Введите «ко» — две игры, пока всё верно. Выберите «Семейные»: на экране по-прежнему «Драконья почта» и «Космические коты», хотя «Коты» — игра для компании. Обработчик категории ничего не знает про `shown`. Чтобы это починить, каждому из четырёх полей пришлось бы повторять фильтрацию по всем четырём фильтрам. Производное значение делает это одной строкой. Верните код решения.

## Как в настоящем проекте

- Признак лишнего состояния: значение можно получить из другого состояния или props, или его обновляют всегда вместе с другим состоянием. Такое значение — `const`.
- «А если вычисление тяжёлое?» Фильтр шести игр — микросекунды. Для тысяч игр сначала измеряют, а потом кэшируют результат: `useMemo` или React Compiler — глава 16. Кэш не меняет правила: значение по-прежнему производное.
- Особенно частая ошибка — копировать props в состояние: `useState(props.items)`. Начальное значение берётся только при первом рендере, и когда `items` изменятся, копия останется старой. Держите props как есть и вычисляйте из них.

::: legacy
В старом коде вы встретите «синхронизацию» производного значения эффектом: `useEffect(() => setShown(filter(games, query)), [query])`. Эффект срабатывает уже после фиксации, а его `setShown` запускает ещё один — лишний — рендер; между ними в DOM старый список. Эффекты — глава 6, а почему такой эффект не нужен, разобрано в её [шаге «Возможно, эффект не нужен»](step:06-effects/06-no-effect).
:::
