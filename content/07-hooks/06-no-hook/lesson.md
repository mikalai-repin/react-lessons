Свои хуки удобны, и после первых двух-трёх хочется выносить в хук всё подряд. Но хук — не единственный и не всегда лучший способ поделиться кодом. В этом шаге — признаки, по которым видно, что хук не нужен, на примерах из магазина. Код шага не меняется.

## Функция без хуков — не хук

В магазине есть `isHit(game)` из `shared/gameRules.ts` и `formatPrice(price)` из `shared/format.ts`. Можно было назвать их `useIsHit` и `useFormatPrice` — «это же логика для компонентов». Но внутри нет ни одного хука, и приставка `use` только вредит. Она обещает правила хуков — и линтер их применит. В `App` хиты считаются так:

```tsx App.tsx
const hits = games.filter(isHit);
```

С «хуком» то же самое станет ошибкой:

```tsx
const hits = games.filter((game) => useIsHit(game));
```

```
React Hook "useIsHit" cannot be called inside a callback.
React Hooks must be called in a React function component or a custom React Hook function
```

Обычную функцию можно вызвать где угодно: в колбэке `filter`, в условии, в обработчике, в другом модуле, в тесте без React. Правило: **приставка `use` — только у функций, которые вызывают хуки**. Нет хуков — обычное имя.

## Один useState — не повод

```tsx
// hooks/useSelectedGame.ts
export function useSelectedGame() {
  return useState<number | null>(null);
}
```

Такой хук ничего не прячет: ни механизма, ни решения. Читателю `App` придётся открыть ещё один файл, чтобы узнать, что там просто `useState`. То же с `useToggle`, `useBoolean` и подобными обёртками над одним хуком. Если в обёртке нет логики — оставьте встроенный хук.

Хук заслуживает своего имени, когда за ним стоит **механизм или решение**, которые иначе пришлось бы повторять или держать в голове:

- синхронизация с внешней системой и очистка (`useDebouncedValue`, `useInView`, `useOnlineStatus`);
- правило, о котором легко забыть (`useLocalStorage`: прочитать при создании, писать при каждом изменении);
- несколько хуков, которые всегда идут вместе.

## Хуки «жизненного цикла»

Пришедшие из классовых компонентов или из Angular часто пишут:

```tsx
export function useMount(fn: () => void) {
  useEffect(() => {
    fn();
  }, []);
}

// в компоненте
useMount(() => track('просмотр', { gameId: game.id }));
```

Выглядит как `ngOnInit`. Но такой хук ломает главную проверку эффектов — зависимости. Линтер ругается внутри `useMount` («missing dependency: 'fn'»), и это предупреждение обычно глушат комментарием. А в местах вызова он молчит: `game.id` в `useMount` не перезапустит эффект при смене игры, и никто об этом не скажет. Это то самое устаревшее замыкание из главы 6, только спрятанное.

Хороший хук называется по **цели**, а не по моменту жизни компонента: `useOnlineStatus`, а не `useWindowEventOnMount`. Внутри он честно перечисляет зависимости, а свежие значения читает через `useEffectEvent`.

## Хук, который возвращает разметку

```tsx
function usePromoBanner() {
  // …
  return <p className={styles.promo}>…</p>;
}
```

Это компонент под чужим именем. У компонента есть своё место в дереве: свои ячейки хуков, свой рендер, `key`. Разметку из хука рисует компонент, который его вызвал, — и каждое обновление внутри «хука» рендерит этот компонент целиком. Разметка — компонентам, логика — хукам.

## Общее состояние — не хук

В шаге про `useLocalStorage` мы видели: два вызова хука — два независимых состояния. Хук делит **код**, а не **данные**. Если корзина нужна шапке, мини-корзине и странице игры одновременно, `useCart()` с `useReducer` внутри не поможет: у каждого компонента будет своя корзина. Для общих данных — контекст (глава 8) или внешнее хранилище (глава 9). А вот хук-обёртка над ними — `useCart()`, который читает контекст, — нормальная практика: она прячет, **откуда** берутся данные.

## Итог: хук или нет

| Хочется | Лучше |
|---|---|
| `useFormatPrice(price)` без хуков внутри | обычная функция `formatPrice` |
| `useSelectedGame()` = один `useState` | встроенный `useState` |
| `useMount(fn)`, `useUpdate(fn)` | `useEffect` с честными зависимостями |
| `usePromoBanner()` возвращает JSX | компонент `<PromoBanner />` |
| одна корзина для всех через хук | контекст или хранилище (главы 8–9) |
| таймер, подписка, наблюдатель в компоненте | **свой хук** |

## Как в настоящем проекте

- Хуки вводят, когда логика повторяется или когда кусок компонента заслуживает имени. Иногда хук используется в одном месте — и всё равно полезен: `App` в магазине уже больше 200 строк, и `useToast()` (уведомление, ссылка на таймер и `showToast`) сделал бы его понятнее. Попробуйте сами: перенесите `toast`, `toastTimer` и `showToast` в `hooks/useToast.ts` и верните из хука `{ toast, showToast }`.
- Прежде чем писать хук, проверьте, нет ли его в библиотеках, которые уже в проекте: роутер, TanStack Query, Zustand дают свои хуки для адреса, данных с сервера и хранилищ.
- Каждый свой хук — публичное API: имя по цели, понятный ответ (значение, пара или объект), стабильные функции на выходе.
