В этом шаге нового кода нет — только эксперименты на магазине из прошлого шага. Они объясняют два правила, на которых держится весь React: **данные текут сверху вниз** и **компонент — чистая функция**. Нарушить оба правила легко: ни TypeScript, ни React вас не остановят. А последствия проявляются в неожиданных местах.

## Данные текут сверху вниз

Посмотрите, откуда карточка берёт игру:

```
data/games.ts
     │ games
     ▼
    App ──── count ────▶ Header
     │
     ├── hits ──▶ Section «Хиты»
     │              └─ game ─▶ GameCard × 3
     └── games ─▶ Section «Все игры»
                    └─ game ─▶ GameCard × 6
```

Данные лежат у `App`, и каждый компонент получает от родителя ровно свою часть. Обратной стрелки нет: карточка не может поменять ни массив игр, ни props родителя. Если дочернему компоненту нужно что-то изменить «наверху» — например, положить игру в корзину, — родитель передаст ему функцию в пропе (`onAdd`), и изменение сделает сам. Так устроены события в главе 4.

Из этого следует правило: **props только для чтения**. Компонент получает их, читает и рисует по ним разметку — но не меняет.

## Эксперимент: мутация props

Нарушим правило. Пусть карточка хита дописывает к своим тегам тег «хит». Добавьте в начало `GameCard`, перед `const { min, max }`:

```tsx shared/GameCard.tsx
if (isHit(game)) game.tags.push('хит');
```

TypeScript промолчал: поле `tags` — обычный массив, менять его можно. Посмотрите на результат:

- в разделе «Хиты» у «Острова сокровищ» теги `#пираты #карты #хит #хит` — два «хита» вместо одного;
- в «Всех играх» у той же игры — **четыре**: `#хит #хит #хит #хит`;
- в консоли — предупреждения `Encountered two children with the same key, `хит`.`

Что произошло? Обе карточки «Острова сокровищ» получили **один и тот же объект** игры из массива `games` — props передают ссылку, а не копию. Каждый вызов `GameCard` дописывал тег в общий массив. Строгий режим вызывает каждый компонент дважды — получилось два тега у первой карточки и ещё два у второй. Одна строчка «безобидного» кода испортила данные всего приложения, и результат зависит от того, сколько раз и в каком порядке React вызвал компоненты. Уберите строку.

А если попробовать изменить сам объект props?

```tsx shared/GameCard.tsx
export function GameCard(props: GameCardProps) {
  props.game = { ...props.game, price: 0 };
  const { game } = props;
```

Ошибки типов снова нет, но приложение упадёт: `TypeError: Cannot assign to read only property 'game' of object '#<Object>'`. В режиме разработки React **замораживает** объект props (`Object.freeze`, как сам элемент — глава 1). Но заморозка неглубокая: поля верхнего уровня защищены, а объект игры внутри — нет. Поэтому `game.tags.push` прошёл, а `props.game =` — нет. Верните `{ game }` в параметр.

::: warning
Надеяться на заморозку нельзя: в продакшен-сборке её нет, а вложенные объекты не заморожены и в разработке. Правило «props только для чтения» держится на дисциплине — и на том, что новые значения вы создаёте, а не меняете старые (подробно — в главе 4).
:::

## Компонент — чистая функция

**Чистая функция** зависит только от своих аргументов и ничего не меняет снаружи: те же входные данные — тот же результат. Компонент React должен быть именно таким: те же props — тот же JSX. Рендер — это **вычисление** разметки, а не место для действий.

Проверим, что будет, если компонент меняет что-то снаружи. Пронумеруем карточки счётчиком на уровне модуля:

```tsx shared/GameCard.tsx {1,4,8}
let rendered = 0;
…
export function GameCard({ game }: GameCardProps) {
  rendered++;
  const { min, max } = game.players;
  …
      <h3 className={styles.cardTitle}>
        №{rendered} {game.title}
      </h3>
```

Ожидаем №1…№9, а видим **№2, №4, №6 … №18**. Строгий режим вызвал каждую карточку дважды и показал результат второго вызова. Уберите `<StrictMode>` из `main.tsx` (замените на `<>…</>`) — номера станут 1…9. Но строгий режим не виноват: он намеренно вызывает компоненты дважды, чтобы такие ошибки было видно сразу. React вправе вызвать компонент сколько угодно раз — при каждом обновлении, повторно после ошибки, заранее «на всякий случай» (в главе 12 вы увидите, как он прерывает и повторяет рендер). Компонент, который при этом что-то меняет снаружи, сломается — не сейчас, так позже. Верните `<StrictMode>` и уберите счётчик.

Что нельзя делать при рендере:

- менять props, переменные модуля, объекты, пришедшие снаружи;
- менять DOM вручную, отправлять запросы, запускать таймеры, писать в `localStorage`.

Что можно: вычислять что угодно из props и создавать **новые** объекты и массивы — как `specs` и `discount` в карточке. Локальные переменные, созданные внутри вызова, никому не мешают.

А где же тогда отправлять запросы и менять данные? В обработчиках событий (глава 4) — они выполняются по действию пользователя, а не при рендере, — и в эффектах (глава 6).

## Как в настоящем проекте

- Можно объявить props неизменяемыми: `Readonly<GameCardProps>` или `readonly` у полей. Тогда `props.game =` подчеркнёт редактор. Но `Readonly` неглубокий, как и заморозка: `game.tags.push` он не поймает, для этого нужен `readonly string[]` в модели. В курсе так не делаем, полагаемся на правило.
- Линтер настоящего проекта находит часть нарушений: в `eslint-plugin-react-hooks` 7 есть правила `react-hooks/purity` (нечистые вызовы при рендере) и `react-hooks/immutability` (изменение props и значений, которые нельзя менять). Настроим его в главе 23. Но и линтер ловит не всё — правило остаётся за вами.

::: tip
В Angular шаблон можно перерисовать сколько угодно раз, но класс компонента создаётся один раз, и менять его поля — обычное дело. В React нет экземпляра, который живёт между рендерами: каждый рендер — новый вызов функции. Всё, что должно пережить вызов, хранит React (состояние — глава 4), а не переменные компонента или модуля.
:::
