Этот шаг необязательный. За главу роутер выбирал маршруты, вызывал загрузчики до показа, отменял запросы и перезагружал данные после действий. Посмотрим, по каким правилам он это делает, — на маленьком стенде без магазина. Замените `main.tsx` кодом ниже (после шага верните прежний кнопкой «Сброс»):

```tsx main.tsx
import { createRoot } from 'react-dom/client';
import {
  createBrowserRouter,
  Link,
  matchRoutes,
  Outlet,
} from 'react-router';
import { RouterProvider } from 'react-router/dom';

// 1. Ранжирование: порядок в массиве не важен
const routes = [
  { path: '/games/:id' },
  { path: '/games/new' },
  { path: '*' },
];
for (const url of ['/games/new', '/games/4', '/games']) {
  const match = matchRoutes(routes, url)?.at(-1);
  console.log(url, '→', match?.route.path, match?.params);
}

// 2. Загрузчики вложенных маршрутов: параллельно
const start = Date.now();
const ms = () => `${Date.now() - start} мс`;
function slow(name: string, delay: number) {
  return async ({ request }: { request: Request }) => {
    console.log(`${name}: начал`, ms());
    request.signal.addEventListener('abort', () =>
      console.log(`${name}: отменён`, ms()),
    );
    await new Promise((r) => setTimeout(r, delay));
    console.log(`${name}: закончил`, ms());
    return name;
  };
}

const router = createBrowserRouter([
  {
    path: '/',
    loader: slow('корень', 1000),
    HydrateFallback: () => <p>Загружаем…</p>,
    Component: () => (
      <>
        <Link to="/a">Раздел A</Link> · <Link to="/b">Раздел B</Link>
        <Outlet />
      </>
    ),
    children: [
      { index: true, Component: () => <p>Главная</p> },
      {
        path: 'a',
        loader: slow('A', 1000),
        Component: () => <p>Раздел A</p>,
      },
      {
        path: 'b',
        loader: slow('B', 300),
        Component: () => <p>Раздел B</p>,
      },
    ],
  },
]);

createRoot(document.getElementById('root')!).render(
  <RouterProvider router={router} />,
);
```

## Сопоставление: очки, а не порядок

Первые три строки консоли:

```
/games/new → /games/new {  }
/games/4 → /games/:id { id: "4" }
/games → * { *: "games" }
```

`/games/:id` стоит в массиве **раньше**, а для `/games/new` выбран `/games/new`. React Router не перебирает маршруты по порядку до первого подходящего, как это делали ранние роутеры (и `<Switch>` в v5). Он **ранжирует**: каждому пути — очки, по сегментам (`rankRouteBranches` в исходниках): статический сегмент (`new`) — 10, параметр (`:id`) — 3, `*` — штраф. Побеждает больше очков; порядок в массиве решает только ничью. Поэтому «Такой страницы нет» на `*` можно ставить где угодно — и `/games/new` никогда не примут за игру с id `new`.

`matchRoutes(маршруты, адрес)` — та же функция, которой роутер пользуется сам: она возвращает **цепочку** совпадений от корня до листа, с параметрами. Мы берём последнее — лист.

## Загрузчики — параллельно

Откройте `/a` в адресной строке:

```
корень: начал 2 мс
A: начал 2 мс
корень: закончил 1005 мс
A: закончил 1005 мс
```

У корня и у раздела по секунде, а вместе — тоже секунда: роутер вызывает загрузчики **всей цепочки сразу**. Если бы раздел ждал корня (как бывает, когда каждый компонент грузит данные сам в `useEffect`), было бы две секунды — это называют **водопадом** запросов. В главе 11 мы его увидим в живую.

## Кого перезагружать

Щёлкните «Раздел B»:

```
B: начал 1354 мс
B: закончил 1656 мс
```

Загрузчик корня **не** вызвался: корневой маршрут остался в цепочке, и его параметры не изменились — роутер считает его данные свежими. Новый загрузчик — только у нового маршрута. А вот после `action` (шаги «Изменение данных» и «useFetcher») роутер перезагружает **все** загрузчики открытой страницы: действие могло изменить что угодно. Это правило по умолчанию, и его меняет `shouldRevalidate` маршрута.

## Отмена: побеждает последний

Вернитесь на `/` (дождитесь «Главная»), щёлкните «Раздел A» и сразу — «Раздел B»:

```
A: начал …
A: отменён …
B: начал …
B: закончил …
A: закончил …
```

Второй переход отменил первый: роутер вызвал `abort` у `request.signal` загрузчика A и забыл о нём. На экране — «Раздел B», адрес `/b`, гонки нет: даже если бы ответ A пришёл позже, роутер его не покажет. Но посмотрите на последнюю строку — **«A: закончил»**. Сигнал только **сообщает** об отмене; наш таймер его не слушает и доработал до конца. Поэтому в `gameLoader` мы передавали `signal` в `fetch` (шаг «Загрузка данных»): тогда отменяется и сам запрос.

## Жизнь перехода

```
щелчок по Link
 │  navigation.state = 'loading'
 ├─ сопоставление: цепочка маршрутов
 ├─ lazy и loader всей цепочки — параллельно
 │   ├─ redirect → новый переход
 │   ├─ throw    → ErrorBoundary
 │   └─ новый щелчок → abort, начать заново
 ├─ данные готовы: адрес в истории
 └─ рендер цепочки, state = 'idle'
```

Отсюда всё, что мы видели в главе: адрес меняется **после** загрузки, старая страница видна до конца перехода, `HydrateFallback` нужен только первому заходу.

## Обзор: TanStack Router

У React Router есть сильный соперник — [TanStack Router](https://tanstack.com/router). Те же идеи (вложенные маршруты, `loader`, ленивые маршруты, отмена), но главное у него — **типы**:

- пути и параметры проверяются TypeScript: `<Link to="/games/$id" params={{ id: 4 }}>` с опечаткой в пути не соберётся (в React Router это есть только в режиме фреймворка);
- параметры поиска описываются схемой (`validateSearch`, хоть Zod) — наш `filtersFromParams` библиотека пишет за вас;
- встроенный кэш загрузчиков и тесная связь с TanStack Query (глава 11).

Цена — больше кода на старте (маршруты по файлам с генерацией или дерево с `createRoute`) и меньшая распространённость. React Router — по-прежнему стандарт, который вы встретите в большинстве проектов, поэтому курс на нём.
