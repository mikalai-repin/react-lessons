Этот шаг необязательный. В шаге про списки мы договорились: ключ — устойчивый id из данных, а не индекс. Здесь проверим на опыте, что именно ломается с индексом, и заглянем в то, как React сопоставляет элементы списков.

## Демо

В шаге новый файл `KeyDemo.tsx`, а `main.tsx` рисует его вместо `App` (магазин вернётся в практикуме). В демо — список из четырёх игр, у каждой поле для заметки, и кнопка «Перевернуть список».

В коде демо есть `useState` и `onClick` — их разберём в главе 4. Пока достаточно знать: по кнопке массив `list` переворачивается, и React рисует список заново. Главное для нас — строка с ключом:

```tsx KeyDemo.tsx
{list.map((game, index) => (
  <li key={index}>
    <label>
      {game.title} <input placeholder="Заметка" />
    </label>
  </li>
))}
```

## Эксперимент: индекс как ключ

1. Напишите в поле у «Острова сокровищ» заметку: «купить к Новому году».
2. Нажмите «Перевернуть список».

Названия перевернулись — «Маяк» теперь первый, «Остров сокровищ» последний. А заметка осталась **в первой строке**, теперь рядом с «Маяком». Данные и интерфейс разошлись: пользователь писал про одну игру, а видит заметку у другой.

## Что сделал React

После нажатия компонент вернул новый список элементов, и React **сверил** его со старым: какие элементы остались, какие появились, какие исчезли. Соответствие он ищет по `key`. С ключом-индексом это выглядит так:

```
ключ  было             стало
0     Остров сокровищ  Маяк
1     Драконья почта   Ночной экспресс
2     Ночной экспресс  Драконья почта
3     Маяк             Остров сокровищ
```

Для React элемент с ключом `0` был и остался: тот же тип `li`, тот же ключ — значит, это **тот же** элемент, у которого поменялось содержимое. Он оставляет на месте DOM-узел `<li>` и меняет в нём текст названия. Поле `<input>` внутри тоже остаётся на месте — а с ним и введённый текст: значение поля хранит браузер в DOM-узле, React о нём не знает. Если понаблюдать за DOM (через `MutationObserver`), видно: React поменял текст в четырёх строках и не переставил ни одного узла.

## Ключ из данных

Замените `key={index}` на `key={game.id}` (и уберите ставший ненужным параметр `index`, иначе TypeScript напомнит: `'index' is declared but its value is never read.`). Повторите эксперимент.

Теперь заметка уехала вместе с «Островом сокровищ» в конец списка. Ключ — id игры — у каждой строки свой и не зависит от позиции:

```
было                   стало
id 1 Остров сокровищ   id 7 Маяк
id 2 Драконья почта    id 4 Ночной экспресс
id 4 Ночной экспресс   id 2 Драконья почта
id 7 Маяк              id 1 Остров сокровищ
```

React находит для каждого нового элемента старый с тем же ключом и **переставляет** DOM-узлы, ничего не пересоздавая. Текст названий менять не нужно — каждый `<li>` уезжает целиком, вместе с полем и его значением.

Ещё один вариант для полноты — `key={Math.random()}`. Нажмите кнопку: заметка пропала совсем. Ключи новые при каждом рендере, ни один не совпал со старым — React удалил все четыре `<li>` и создал четыре новых, с пустыми полями. Это и неправильно, и медленно. Верните `key={game.id}`.

## Как React сопоставляет список

Алгоритм сверки списка (функция `reconcileChildrenArray` в `react-dom`) устроен примерно так:

1. Идёт по старому и новому списку **одновременно**, пока ключи на одинаковых позициях совпадают. Чаще всего список меняется в конце (добавили элемент), и этот проход справляется сам.
2. На первом несовпадении складывает оставшиеся старые элементы в `Map` по ключу (у элементов без ключа ключ — позиция).
3. Для каждого следующего нового элемента ищет в `Map` старый с тем же ключом. Нашёлся, и тип тот же — DOM-узел переиспользуется, меняются только props. Не нашёлся — узел создаётся.
4. Старые элементы, которые остались в `Map`, удаляются из DOM.

Какие узлы двигать, React решает за один проход: он помнит самую дальнюю старую позицию среди уже расставленных элементов. Новый «Маяк» был на позиции 3 — он остаётся на месте. «Ночной экспресс» был на позиции 2, раньше «Маяка», — его нужно переставить, и так же остальные два. Поэтому при перевороте четырёх строк React делает **три** перестановки, а не четыре. (Наблюдение за DOM это подтверждает: три узла вынуты и вставлены заново.)

Отсюда практические выводы:

- **Ключ — это идентичность элемента**, а не номер в списке. Тот же ключ — тот же элемент со всем его DOM-состоянием (поля, фокус, прокрутка) и, как вы увидите дальше, со всем состоянием компонента.
- **Индекс как ключ** безопасен, только если список никогда не переставляется, не фильтруется и в его элементах нет состояния: тогда позиция и есть идентичность. Во всех остальных случаях — id из данных.
- **Нет id в данных** (например, новые строки формы до сохранения) — создайте его при добавлении элемента (`crypto.randomUUID()`) и храните вместе с данными. Генерировать ключ при рендере нельзя — это `Math.random()` из эксперимента.
- Сверка сравнивает только **соседей одного родителя**. Ключи не обязаны быть уникальными на всей странице, и элемент не может «переехать» с ключом в другой список.

Позже `key` пригодится и вне списков: смена ключа — способ сказать React «это другой элемент, начни с чистого листа». Этим приёмом сбрасывают состояние формы при смене игры — в главе 5.

::: tip
Это тот же механизм, что `track` в `@for` у Angular: там тоже `track $index` ведёт к перепутанному состоянию строк, а `track game.id` — нет. React и Angular сопоставляют списки по одному принципу.
:::
