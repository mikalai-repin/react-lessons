Маркетологи прислали текст акции для баннера над каталогом. Текст готовят в своей системе, и в нём есть разметка — важное выделено жирным:

```tsx
// Текст акции готовят маркетологи в своей системе — с HTML-разметкой
const PROMO_HTML =
  'Неделя семейных игр: скидки до <b>20%</b> на «Остров сокровищ» и «Нарды»';
```

Посмотрим, что React делает с HTML внутри данных и почему по умолчанию он такой осторожный.

## Выражения в JSX экранируются

Сначала выведем текст обычным выражением — добавьте в начало `<main>`:

```tsx
<p className={styles.promo}>{PROMO_HTML}</p>
```

На экране `…скидки до <b>20%</b> на…` — теги показаны как текст. Всё, что попадает в JSX через фигурные скобки, React вставляет **как текст**: записывает строку в текстовый узел, и браузер не разбирает её как HTML. Если заглянуть в `innerHTML` абзаца, там будет `&lt;b&gt;20%&lt;/b&gt;` — угловые скобки заменены на коды, это и называется **экранированием**.

Это не неудобство, а защита. Представьте, что строка пришла от пользователя (например, это отзыв об игре), и там написано `<img src="x" onerror="украсть данные">`. Если бы JSX вставлял HTML, код злоумышленника выполнился бы в браузере каждого посетителя. Такая атака называется **XSS** (cross-site scripting, межсайтовый скриптинг) — одна из самых частых уязвимостей веб-приложений. С выражениями в JSX она невозможна — ни в тексте, ни в атрибутах.

## dangerouslySetInnerHTML

Если разметку всё-таки нужно показать, в React есть атрибут с говорящим названием:

```tsx App.tsx
<p
  className={styles.promo}
  dangerouslySetInnerHTML={{ __html: PROMO_HTML }}
/>
```

«Опасно установить innerHTML». Неудобное имя и объект с полем `__html` вместо простой строки — нарочно: такую строку не напишешь случайно, и её легко найти поиском по проекту при проверке безопасности. React запишет строку в `innerHTML` элемента **как есть**. Своего содержимого у такого элемента быть не может — поэтому тег закрыт сразу, `/>`.

::: task
1. Объявите над компонентом константу `PROMO_HTML` с текстом акции (скопируйте из начала шага).
2. Первым элементом `<main>` добавьте абзац с классом `styles.promo` и выведите в него `PROMO_HTML` через `dangerouslySetInnerHTML`.
:::

## Что получилось

Над каталогом — жёлтый баннер, «20%» выделено жирным.

Эксперимент: допишите внутрь `<p>` текст, например `<p …>Акция</p>`. React упадёт с ошибкой ``Can only set one of `children` or `props.dangerouslySetInnerHTML`.`` — содержимое у элемента может быть одно: либо дочерние элементы, либо HTML-строка. TypeScript такую ошибку не ловит. Верните `/>`.

## Эксперимент: взломайте магазин

Допишите в конец `PROMO_HTML` опасную разметку (внутри строки в одинарных кавычках — двойные):

```html
<img src="x" onerror="console.log('XSS: чужой код выполнен')"><script>console.log('XSS из script')</script>
```

В консоли появится **«XSS: чужой код выполнен»**. Картинка с адресом `x` не загрузилась, сработал обработчик `onerror` — и выполнился код, пришедший в данных. Второй строки нет: `<script>`, вставленный через `innerHTML`, браузер не запускает. Но атаке хватает и одного `onerror`.

**React не очищает HTML.** Это главное отличие от Angular, где `[innerHTML]` проходит санитизацию и `onerror` был бы вырезан. В React `dangerouslySetInnerHTML` означает ровно то, что написано: вы отвечаете за содержимое сами. Уберите опасную разметку.

::: warning
Правило: в `dangerouslySetInnerHTML` попадает только HTML из **доверенного** источника — своего, проверенного. Всё, что ввёл пользователь (отзывы, имена, комментарии), выводится только через `{}`. Если HTML от пользователя всё-таки нужен (например, редактор с форматированием), его очищают специальной библиотекой — чаще всего [DOMPurify](https://github.com/cure53/DOMPurify): `dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }}`.
:::

## Ссылки javascript:

Есть и второй путь атаки — адрес ссылки. `href="javascript:…"` при щелчке выполняет код. Если адрес пришёл из данных (сайт издателя, ссылка на правила), злоумышленник может подставить туда код. Проверьте, что сделает React, — добавьте над баннером:

```tsx
<a href={"javascript:console.log('XSS из ссылки')"}>Правила акции</a>
```

Ссылка появилась, но щелчок по ней кода не выполнит. В консоли ошибка: `React has blocked a javascript: URL as a security precaution.` React 19 подменяет такие адреса в `href`, `src`, `action` и `formAction` на код, который бросает эту ошибку. Посмотрите сами: `setTimeout(() => console.log(document.querySelector('a')?.getAttribute('href')), 100);` напечатает `javascript:throw new Error('React has blocked a javascript: URL as a security precaution.')`.

Но защита работает только для атрибутов, которые ставит **React**. Перенесите ту же ссылку внутрь `PROMO_HTML` — `<a href="javascript:console.log(…)">Правила</a>` — и щёлкните: код выполнится. HTML внутри `dangerouslySetInnerHTML` React не разбирает и не проверяет. Уберите ссылку и строку с `setTimeout`.

::: tip Как в настоящем проекте
- В коде `dangerouslySetInnerHTML` встречается редко и почти всегда рядом с очисткой (DOMPurify) или с HTML, который собрал свой же сервер (например, статья из CMS). Проверка безопасности начинается с поиска этого слова по проекту.
- Ещё одна дыра — запись в DOM в обход React: `element.innerHTML = …` через ссылку на элемент (ссылки на DOM — глава 6). Там тоже нет никакой защиты.
- Адреса из данных стоит проверять и самим: разрешать только `http:` и `https:` (`new URL(href).protocol`). React блокирует `javascript:`, но не, например, `data:`-адреса в ссылках.
:::

::: legacy Вы встретите в старом коде
До React 19 ссылки `javascript:` только вызывали предупреждение в консоли, а щелчок выполнял код. Если в старом проекте адреса приходят из данных, проверка протокола могла быть единственной защитой — не удаляйте её при обновлении.
:::
