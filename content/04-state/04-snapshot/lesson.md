В этом шаге нового кода нет — только эксперименты. Они отвечают на вопрос, на котором спотыкается почти каждый, кто начинает писать на React: почему сразу после `setQuantity` переменная `quantity` всё ещё старая?

## Эксперимент: три вызова подряд

Пусть кнопка добавляет сразу три штуки. Кажется, достаточно вызвать сеттер три раза:

```tsx shared/GameCard.tsx {3-6}
  // Щелчок по «В корзину»
  function handleAddClick() {
    setQuantity(quantity + 1);
    setQuantity(quantity + 1);
    setQuantity(quantity + 1);
    console.log('после set:', quantity);
  }
```

Нажмите «В корзину» у «Острова сокровищ». На экране «В корзине: 1 шт.», а не 3. В консоли:

```
после set: 0
render Остров сокровищ 1
render Остров сокровищ 1
```

(Строки `render` — от `console.log('render', game.title, quantity)` сразу после `useState`, как в шаге `useState`; добавьте его для этого эксперимента.)

Сеттер не изменил `quantity`: после трёх вызовов там всё ещё 0. Рендер был один, и в нём `quantity` стало 1.

## Каждый рендер — снимок

Вспомните, что такое рендер: React вызывает функцию `GameCard`. В этом вызове `useState` вернул число — скажем, 0 — и положил его в константу `quantity`. Все функции, объявленные в этом вызове, включая `handleAddClick`, видят **именно эту константу**. Это обычное замыкание JavaScript: функция помнит переменные того вызова, в котором её создали.

Поэтому состояние называют **снимком** (snapshot): каждый рендер получает свои значения props и состояния, и внутри рендера они не меняются. Сеттер не трогает переменную — он просит React **в следующем рендере** вернуть из `useState` новое значение.

Теперь три вызова читаются так:

```
рендер 1: quantity = 0
  щелчок → handleAddClick из рендера 1
    setQuantity(0 + 1)  → «дальше будет 1»
    setQuantity(0 + 1)  → «дальше будет 1»
    setQuantity(0 + 1)  → «дальше будет 1»
    console.log(0)
рендер 2: quantity = 1
```

## Эксперимент: значение через три секунды

Снимок не обновляется, даже если подождать. Замените тело обработчика:

```tsx shared/GameCard.tsx
  function handleAddClick() {
    setQuantity(quantity + 1);
    setTimeout(() => console.log('через 3 с:', quantity), 3000);
  }
```

Быстро нажмите «В корзину» три раза. На экране сразу «3 шт.», а через три секунды в консоли:

```
через 3 с: 0
через 3 с: 1
через 3 с: 2
```

Каждый щелчок обработал свой `handleAddClick` — из рендера, который был на экране в момент щелчка. Он и через три секунды помнит значение того рендера. Состояние к этому времени давно 3, но старые замыкания об этом не знают.

## Почему так задумано

Снимок защищает от «полуобновлённых» данных. Пока обработчик выполняется, всё, что он читает, согласовано: `quantity`, `game`, props и всё, что вычислено при рендере, относится к одному и тому же моменту — тому, что видел покупатель, когда нажал кнопку. Проверка вроде `if (quantity < game.inStock)` не сломается от того, что где-то посередине обработчика значение «вдруг» стало другим.

Цена — новое правило: **после вызова сеттера переменная состояния не меняется**. Если новое значение нужно дальше в обработчике, сохраните его в свою переменную:

```tsx
const next = quantity + 1;
setQuantity(next);
console.log(next); // 1 — то, что будет в следующем рендере
```

Уберите эксперименты: обработчик снова один раз вызывает `setQuantity(quantity + 1)`, без таймера и `console.log`.

## Как в настоящем проекте

- Ошибка «прочитал состояние сразу после `set` и получил старое» — одна из самых частых у новичков в React. Ни TypeScript, ни React о ней не предупредят.
- Тот же снимок встретится в эффектах и таймерах (глава 6): функция, созданная в старом рендере, видит старые значения. Это называют **устаревшим замыканием** (stale closure).

::: tip
Сигнал Angular — живой объект: `count()` всегда возвращает текущее значение, и после `count.set(1)` следующая строка уже прочитает 1. Состояние React — не объект, а значение в константе рендера. Отсюда и разница: в React «текущее» значение появляется только вместе с новым рендером.
:::
