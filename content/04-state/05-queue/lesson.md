Три `setQuantity(quantity + 1)` подряд дали +1, потому что каждый вызов прочитал один и тот же снимок. Но сеттер умеет принимать не только значение, но и **функцию**. С ней три вызова дадут +3.

## Функция обновления

```tsx shared/GameCard.tsx
  function handleAddClick() {
    setQuantity((q) => q + 1);
    setQuantity((q) => q + 1);
    setQuantity((q) => q + 1);
  }
```

Нажмите «В корзину»: «В корзине: 3 шт.». `(q) => q + 1` — **функция обновления** (updater function). Она не читает снимок `quantity`, а получает **результат предыдущего обновления** в параметре.

Сеттер ничего не меняет сразу — он кладёт обновление в **очередь** компонента. При следующем рендере `useState` разбирает очередь по порядку: значение просто заменяет текущее, а функция вызывается с текущим и возвращает новое.

| Очередь | Разбор | Итог |
|---|---|---|
| `q => q + 1` ×3 | 0 → 1 → 2 → 3 | 3 |
| `quantity + 1` ×3 (при 0) | заменить на 1, на 1, на 1 | 1 |
| `quantity + 5`, затем `q => q + 1` | заменить на 5, затем 5 + 1 | 6 |
| `q => q + 1`, затем `42` | 0 + 1, затем заменить на 42 | 42 |

Каждую строку таблицы можно проверить, подставив вызовы в `handleAddClick`.

Параметр функции обновления называют коротко — первой буквой состояния (`q`, `n`) или `prev`. Важно другое: внутри функции читайте **только параметр**, а не `quantity` из снимка.

## Функция обновления должна быть чистой

Выведите что-нибудь из функции обновления:

```tsx shared/GameCard.tsx
setQuantity((q) => {
  console.log('updater', q);
  return q + 1;
});
```

Один щелчок — и в консоли `updater 0` **дважды**, а счётчик вырос на 1. Строгий режим вызывает функцию обновления два раза, как и сам компонент, и берёт один результат. Если функция чистая — ничего не меняет снаружи и возвращает результат только из параметра, — второй вызов ничего не портит. Если она что-то меняет, строгий режим это покажет. В шаге про массивы мы увидим такую ошибку.

## Пакетная обработка

Сколько рендеров вызвали три `setQuantity` подряд? Добавьте после `useState` строку `console.log('render', game.title, quantity)` и нажмите кнопку:

```
render Остров сокровищ 3
render Остров сокровищ 3
```

Один рендер (две строки — строгий режим), а не три. React не начинает рендер посреди обработчика: он собирает все обновления, а когда обработчик закончился, рисует один раз уже с итоговым значением. Это называется **пакетной обработкой обновлений** (batching).

Так же React поступает и вне обработчиков. Перенесите обновления в таймер:

```tsx shared/GameCard.tsx
  function handleAddClick() {
    setTimeout(() => {
      setQuantity((q) => q + 1);
      setQuantity((q) => q + 1);
      console.log('в таймере');
    }, 0);
  }
```

В консоли `в таймере`, затем один рендер со значением 2. То же — после `await` в асинхронном обработчике: два обновления, один рендер.

## Где функция обновления действительно нужна

Три вызова подряд в одном обработчике — редкость. Чаще функция обновления спасает от устаревшего снимка в отложенном коде. Добавление «с задержкой»:

```tsx shared/GameCard.tsx
setTimeout(() => setQuantity(quantity + 1), 1000);
```

Нажмите «В корзину» у «Драконьей почты» дважды подряд, быстрее чем за секунду. Через секунду — «1 шт.»: оба таймера взяли `quantity` из одного и того же снимка (0) и оба записали 1. Замените на `setQuantity((q) => q + 1)` — после двух щелчков «2 шт.»: функции обновления не зависят от снимка, каждая получила результат предыдущей.

Правило курса: **если новое значение считается из старого, передавайте функцию обновления**. Если вы задаёте значение, не глядя на старое (`setQuantity(0)`, `setIsOpen(true)`), — передавайте значение.

::: task
Верните обработчик к одному обновлению и перепишите его на функцию обновления: `setQuantity((q) => q + 1)`. Уберите `console.log` и эксперименты.
:::

## Что получилось

Внешне ничего не изменилось: щелчок добавляет одну штуку, у «Ночного экспресса» кнопка выключается на трёх. Но обработчик больше не зависит от снимка: его можно вызвать из таймера, после запроса или несколько раз подряд.

## Как в настоящем проекте

- Функцию обновления пишут почти всегда, когда следующее значение зависит от предыдущего: счётчики, переключатели (`setOpen((o) => !o)`), добавление в массив. Линтер этого не требует — это привычка.
- Пакетная обработка автоматическая: в обработчиках, таймерах, промисах. Специально «группировать» обновления не нужно.

::: deep flushSync: обновить DOM прямо сейчас
Иногда новый DOM нужен сразу после обновления — например, прокрутить список к только что добавленной строке. Для этого есть `flushSync` из `react-dom`:

```tsx
import { flushSync } from 'react-dom';

flushSync(() => setQuantity((q) => q + 1));
// здесь DOM уже обновлён: «В корзине: 1 шт.»
setQuantity((q) => q + 1);
```

В логе это два отдельных рендера: первый — внутри `flushSync`, до следующей строки обработчика, второй — после обработчика. `flushSync` отключает пакетную обработку и заставляет React рендерить синхронно, поэтому его берут только тогда, когда без него нельзя.
:::

::: legacy До React 18
В React 17 и раньше пакетная обработка работала только внутри обработчиков React. Два `setState` в `setTimeout` или после `await` давали два рендера, и в старом коде можно встретить `unstable_batchedUpdates` из `react-dom` — ручную пакетную обработку. С `createRoot` (React 18+) она не нужна: пакетная обработка автоматическая везде.
:::
