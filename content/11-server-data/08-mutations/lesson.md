Форма отзыва на странице игры до сих пор притворяется: «Спасибо! Отзыв появится после проверки» — а на сервер ничего не уходит. Учебный бэкенд принимает отзывы: `POST /api/games/:id/reviews` с телом `{ rating, text }` отвечает созданным отзывом (`201`). Без входа автор — «Гость»; вход появится в главе 14.

Что изменилось за кадром: форма переехала из `GameDetails` в свой компонент `game/ReviewForm.tsx` и получила выбор оценки — сервер без неё отзыв не примет. `GamePage` рисует её под отзывами с `key={id}`, как раньше `GameDetails`. В `api/client.ts` появилась `apiPost` (та же обработка ошибок, что у `apiGet`), в `api/games.ts` — `postReview(id, review)`, в моделях — `NewReview`: оценка и текст.

## Запросы и мутации

До сих пор мы только **читали**: `useQuery` сам решает, когда спросить сервер, хранит ответ в кэше, повторяет при сбое. Запрос, который **меняет** данные на сервере, устроен иначе — в Query это **мутация** (mutation):

- выполняется только по команде — когда покупатель нажал «Отправить»;
- результат не кэшируется по ключу;
- по умолчанию **не повторяется** при ошибке: повторная отправка отзыва — второй отзыв.

```tsx game/ReviewForm.tsx
  const queryClient = useQueryClient();
  // Мутация — запрос, который меняет данные на сервере
  const addReview = useMutation({
    mutationFn: (review: NewReview) =>
      postReview(gameId, review),
    // Отзыв принят — список отзывов в кэше устарел:
    // Query пометит его и загрузит заново
    onSuccess: () =>
      queryClient.invalidateQueries({
        queryKey: gameKeys.reviews(gameId),
      }),
  });
```

`useMutation` возвращает объект с функцией **`mutate(переменные)`** и состоянием последнего вызова: `isPending`, `isError` и `error`, `isSuccess`, `data`. `useQueryClient()` — тот же `queryClient` из провайдера.

## Инвалидация

Сервер принял отзыв — но в кэше лежит старый список отзывов, и он свежий ещё 30 секунд. Можно было бы дописать новый отзыв в кэш руками, но проще и надёжнее спросить сервер. **`invalidateQueries`** помечает записи устаревшими и сразу перезапрашивает те из них, что сейчас на экране. Записи выбираются **по началу ключа**: `gameKeys.reviews('1')` — это отзывы первой игры, а `gameKeys.detail('1')` накрыл бы и игру, и её отзывы. Вот зачем ключам иерархия.

Обратите внимание: `onSuccess` **возвращает** промис `invalidateQueries`. Возвращённый промис мутация дожидается — и остаётся `isPending`, пока новый список не придёт. Кнопка показывает «Отправляем…» до момента, когда отзыв появится в списке.

## Отправка

```tsx game/ReviewForm.tsx
  function handleSubmit(e: SubmitEvent<HTMLFormElement>) {
    e.preventDefault();
    // Черновик стираем, только когда сервер принял отзыв
    addReview.mutate(
      { rating, text },
      { onSuccess: () => setText('') },
    );
  }
```

У `mutate` второй аргумент — колбэки **этого вызова**. Удобное разделение: в `useMutation` — то, что касается данных (кэш), в `mutate` — то, что касается интерфейса (очистить поле, закрыть окно). Черновик стираем только после успеха — при ошибке текст не пропадёт.

Состояния — в разметке формы: кнопка выключена и говорит «Отправляем…», пока `isPending`; после успеха — «Спасибо за отзыв!»; при ошибке — её текст с `role="alert"`:

```tsx game/ReviewForm.tsx
      {addReview.isError && (
        <p className={styles.error} role="alert">
          Не удалось отправить: {addReview.error.message}
        </p>
      )}
```

`error` типизирован как `Error` — у Query 5 тип ошибки по умолчанию `Error`, а не `unknown`.

::: task
1. В `ReviewForm` замените состояние `sent` мутацией `useMutation` с `mutationFn` через `postReview` и `onSuccess`, который **возвращает** `queryClient.invalidateQueries({ queryKey: gameKeys.reviews(gameId) })`.
2. В `handleSubmit` вызовите `addReview.mutate({ rating, text }, { onSuccess: () => setText('') })`.
3. Кнопка: выключена при пустом тексте **или** `isPending`, подпись «Отправляем…» / «Отправить». Под формой: «Спасибо за отзыв!» при `isSuccess` и «Не удалось отправить: …» при `isError`.
:::

## Что получилось

У шага задержка 800 мс. Напишите отзыв об «Острове сокровищ» и нажмите «Отправить». Кнопка — «Отправляем…» около полутора секунд: во «Сети» сначала `POST /api/games/1/reviews` → 201, затем `GET /api/games/1/reviews` → 200. Затем в списке появляется третий отзыв — от «Гостя», с сегодняшней датой, — поле пустеет, под формой «Спасибо за отзыв!».

## Эксперименты

1. **`onSuccess` без `return`.** Оберните тело в фигурные скобки: `onSuccess: () => { queryClient.invalidateQueries(…); }`. Отправьте отзыв: кнопка вернётся к «Отправить» через 0,8 с, а отзыв появится в списке ещё через 0,8 — мутация закончилась, не дождавшись списка. Верните `return`.
2. **Ошибка.** Включите «Ошибка 500» и отправьте отзыв. Во «Сети» — **один** `POST` с ответом 500, повторов нет. Под формой — «Не удалось отправить: Сервер недоступен (ошибка включена во вкладке «Сеть»)», текст в поле остался. Снимите флажок и отправьте снова.
3. **Без инвалидации.** Уберите `onSuccess` из `useMutation` целиком. Отзыв отправлен (201), а в списке его нет. Уйдите в каталог и вернитесь на игру — всё равно нет: запись отзывов свежая, Query не видит причин спрашивать сервер. Кэш не знает, что вы что-то изменили, — об этом ему говорит инвалидация. Верните.

## Как в настоящем проекте

- Инвалидация после мутации — основной способ держать кэш в согласии с сервером. Ключи-иерархии позволяют одной строкой сбросить всё связанное: после изменения игры в админке (глава 18) — `gameKeys.all`, и каталог, и страница игры, и отзывы.
- Если ответ мутации содержит новые данные целиком (например, `PUT` возвращает обновлённую игру), их кладут прямо в кэш через `setQueryData` — без лишнего запроса.
- Мутации по умолчанию не повторяются: повтор безопасен, только если запрос **идемпотентен** (повторный вызов ничего не меняет). `retry` можно включить у конкретной мутации.
