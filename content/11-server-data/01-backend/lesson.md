До сих пор каталог магазина — шесть игр в массиве `data/games.ts`, и только страница игры с главы 10 спрашивает сервер. В настоящем магазине всё наоборот: игры, цены, остатки и отзывы живут на сервере и меняются без нового выпуска приложения. В этой главе магазин переедет на сервер целиком — и по дороге мы наступим на все грабли, ради которых придуманы Suspense, границы ошибок и TanStack Query.

## Что умеет сервер

Внутри превью работает учебный бэкенд: превью перехватывает каждый `fetch` на адрес `/api/…` и отвечает данными магазина. В каталоге сервера **40 игр** — у нас локально было шесть. Нам понадобятся:

| Запрос | Ответ |
|---|---|
| `GET /api/games` | страница каталога: `{ items, total, page, size }` |
| `GET /api/games/:id` | одна игра; нет такой — `404` |
| `GET /api/games/:id/reviews` | отзывы об игре — массив |
| `POST /api/games/:id/reviews` | новый отзыв (шаг «Изменения на сервере») |

У списка есть параметры: `q` (поиск по названию и тегам), `category`, `inStock=true`, `rating=4.6` (не ниже), `sort` (`price`, `-price`, `rating`, `title`), `page` и `size` — номер и размер страницы, по умолчанию 12 игр. Ошибка — всегда JSON вида `{ "message": "Игра не найдена" }`.

Всё, что сервер получил и ответил, видно во вкладке **«Сеть»** под превью: метод, адрес, код ответа и время. Щёлкните строку — увидите тело ответа. Там же две настройки: **«Задержка»** (0, 300, 1000 или 3000 мс — сеть бывает медленной) и флажок **«Ошибка 500»** — сервер «упал» и на всё отвечает ошибкой. Некоторые шаги главы сами просят сервер ответить на один адрес медленнее или всегда с ошибкой — так мы будем воспроизводить гонки и сбои по заказу.

::: tip Что изменилось за кадром
Корзина раньше хранила только `id` игры, а название и цену искала в `data/games.ts`. С сервером так не выйдет: игры 13 в локальном массиве нет. Поэтому корзина теперь хранит **снимок** игры — `CartGame` в `api/models.ts`: `id`, название, цену, старую цену и остаток на момент добавления. Так делают и настоящие магазины, а итоговую цену при заказе всё равно проверяет сервер. Действие `add` принимает игру целиком, `summarizeCart` больше не нужен каталог, у сохранённой корзины — `version: 2` (старые позиции без цены не восстановить — корзина начинается пустой).
:::

## Один fetch на всё приложение

`fetch` легко вызвать прямо в компоненте или загрузчике. Но у него есть ловушка: **ответ 404 или 500 — не ошибка**. Промис `fetch` отклоняется, только если ответа нет совсем: сеть пропала или запрос отменили. Сервер ответил «игры нет» — `fetch` выполнился успешно, и проверять `response.ok` нужно самим. Забыть об этом в одном из двадцати мест — легко.

Поэтому соберём запросы в одном модуле. Ошибку ответа сделаем настоящим исключением со своим классом — его можно узнать через `instanceof` и прочитать код:

```tsx api/client.ts
/** Сервер ответил ошибкой: код ответа и сообщение из тела */
export class ApiError extends Error {
  status: number;

  constructor(status: number, message: string) {
    super(message);
    this.status = status;
  }
}

/** GET /api/… → данные ответа. Ответ не 2xx — ApiError.
 *  signal отменит запрос, если ответ больше не нужен */
export async function apiGet<T>(
  path: string,
  signal?: AbortSignal,
): Promise<T> {
  const response = await fetch(`/api${path}`, { signal });
  if (!response.ok) {
    // Учебный сервер кладёт текст ошибки в поле message
    const body = (await response.json()) as { message: string };
    throw new ApiError(response.status, body.message);
  }
  return (await response.json()) as T;
}
```

`apiGet<Game>` — обещание, а не проверка: TypeScript поверит, что пришла игра, но сервер может прислать что угодно. Проверять ответ схемой мы научимся в главе 13.

Адреса API — тоже в одном месте, в `api/games.ts`:

```tsx api/games.ts
/** Одна игра по id: GET /api/games/:id */
export function fetchGame(id: string, signal?: AbortSignal) {
  return apiGet<Game>(`/games/${id}`, signal);
}
```

Загрузчик страницы игры стал одной строкой. Нет игры — `fetchGame` бросит `ApiError`, и её поймает граница ошибок маршрута:

```tsx game/GamePage.tsx
export function gameLoader({
  params,
  request,
}: LoaderFunctionArgs) {
  return fetchGame(params.id!, request.signal);
}
```

А `RouteError` научим узнавать код в нашей ошибке — так же, как в ответе `throw data(…)` роутера:

```tsx layout/RouteError.tsx
  // Код ответа: от роутера (throw data(…)) или от нашего apiGet
  const status = isRouteErrorResponse(error)
    ? error.status
    : error instanceof ApiError
      ? error.status
      : null;
  if (status === 404) {
    return <NotFoundPage />;
  }
```

::: task
1. В `api/client.ts` напишите класс `ApiError` и функцию `apiGet`.
2. В `api/games.ts` — функцию `fetchGame`.
3. В `game/GamePage.tsx` замените тело `gameLoader` вызовом `fetchGame(params.id!, request.signal)`.
4. В `layout/RouteError.tsx` вычислите `status` и для `isRouteErrorResponse`, и для `ApiError`; «Сервер ответил ошибкой …» показывайте, когда `status` не `null`.
:::

## Эксперименты

1. **`fetch` не бросает на 404.** Уберите из `apiGet` весь блок `if (!response.ok) { … }` и откройте `/games/999`. Вместо «Такой страницы нет» — «Ошибка в приложении — мы уже знаем о ней.», а в консоли:

   ```
   TypeError: Cannot destructure property 'min' of 'game.players' as it is undefined.
   ```

   Загрузчик вернул тело ошибки `{ message: 'Игра не найдена' }` как игру, и `GameDetails` упал на `game.players`. Ошибка всплыла далеко от причины — вот почему `response.ok` проверяют в одном месте. Верните блок.
2. **Медленная сеть.** Поставьте задержку 3000 мс и щёлкните ссылку на игру в «Хитах». Три секунды главная приглушена (`aria-busy` из главы 10), потом — игра. Во «Сети» видно, сколько шёл запрос. Верните 300.

## Как в настоящем проекте

- Модуль-клиент API есть почти в каждом проекте: базовый адрес сервера, общие заголовки, токен (глава 14), разбор ошибок. Компоненты и загрузчики не вызывают `fetch` напрямую.
- Вместо своего `apiGet` часто берут библиотеку — например, axios: он сам бросает ошибку на 4xx/5xx и умеет «перехватчики» для токена. Чем это отличается от `fetch`, — в шаге «Под капотом».
- Свой класс ошибки с кодом — обычная практика: по нему интерфейс решает, что показать (404 — «не найдено», 401 — «войдите», 500 — «попробуйте позже»).
