В шаге «fetch в эффекте» мы составили список того, чего не умеет загрузка в эффекте: кэш, общий доступ, повторы, обновление, ручные состояния. Всё это — задачи одного рода. Данные с сервера в приложении — не «наше» состояние, а **копия** чужого: она устаревает, её надо перезапрашивать, делить между компонентами и выбрасывать, когда она никому не нужна. Такое состояние называют **серверным** (server state) — в отличие от клиентского, вроде корзины или темы, которым приложение владеет само.

Для серверного состояния есть отдельный инструмент — [TanStack Query](https://tanstack.com/query/latest) (раньше назывался React Query; в курсе — версия 5.104). Это **кэш запросов**: по ключу он хранит ответ, знает, свежий ли он, кто его сейчас показывает, и сам решает, когда спросить сервер снова.

## Клиент и провайдер

Кэш живёт в объекте `QueryClient` — один на приложение. Создадим его в своём модуле: он понадобится и вне компонентов (в загрузчиках роутера):

```tsx api/queryClient.ts
// Клиент TanStack Query — один на приложение: в нём живёт кэш
// всех запросов. Отдельный модуль: клиент понадобится и вне React
export const queryClient = new QueryClient();
```

Компонентам клиент передаёт провайдер — контекст из главы 8:

```tsx main.tsx
        {/* Кэш запросов — всем компонентам приложения */}
        <QueryClientProvider client={queryClient}>
          <RouterProvider router={router} />
        </QueryClientProvider>
```

## useQuery

Запрос описывают двумя полями: **что** загружаем — ключ, и **как** — функция:

```tsx catalog/CatalogPage.tsx
  // Запрос каталога: ключ — что загружаем, queryFn — как.
  // Новый ключ — новый запрос; signal Query отменит сам
  const catalog = useQuery({
    queryKey: ['games', apiParams],
    queryFn: ({ signal }) => fetchGames(apiParams, signal),
  });
```

- **`queryKey`** — массив, который однозначно описывает данные. Всё, от чего зависит ответ, должно быть в ключе: здесь — параметры фильтров. Сменились фильтры — новый ключ — новая запись в кэше и новый запрос. Старая запись остаётся в кэше.
- **`queryFn`** — функция, которая возвращает промис с данными и **бросает** ошибку при неудаче (наш `apiGet` так и делает). Аргументом она получает `signal`: если ответ больше никому не нужен, Query сам отменит запрос. `AbortController`, очистка, проверка `aborted` — всё это теперь внутри библиотеки.

`useQuery` возвращает объект результата. Главные поля:

| Поле | Что значит |
|---|---|
| `data` | данные; `undefined`, пока их нет |
| `isPending` | данных ещё нет (первая загрузка этого ключа) |
| `isError`, `error` | запрос не удался (после повторов) |
| `isFetching` | запрос в полёте — и первый, и фоновый, когда данные уже на экране |
| `refetch()` | спросить сервер снова |

`isPending` и `isFetching` — разные вопросы: «есть ли что показать?» и «идёт ли сейчас запрос?». Есть и `isLoading` — это `isPending && isFetching` (данных нет и запрос идёт).

Разметка почти не изменилась. TypeScript знает: после проверок `isPending` и `isError` поле `data` — точно `Page<Game>`:

```tsx catalog/CatalogPage.tsx

          <Button onClick={() => catalog.refetch()}>
            Повторить
          </Button>

      ) : catalog.data.items.length === 0 ? (
```

## Общие данные: шапка

Шапка всё ещё пишет «в каталоге 6 игр» — число из локального массива. Настоящее число — `total` того же запроса каталога. Шапка просто вызывает `useQuery` с **тем же ключом**:

```tsx layout/Header.tsx
  // Сколько игр в каталоге: тот же ключ, что у каталога без фильтров, —
  // одна запись в кэше и один запрос на двоих
  const catalog = useQuery({
    queryKey: ['games', ''],
    queryFn: ({ signal }) => fetchGames('', signal),
  });
```

Один ключ — одна запись. Сколько бы компонентов ни спросили её одновременно, запрос уйдёт один (это называют **дедупликацией**), а ответ получат все. Пропа `count` у шапки больше нет — `Layout` рисует просто `<Header />` и не импортирует `data/games`.

::: task
1. В `api/queryClient.ts` создайте и экспортируйте `queryClient`.
2. В `main.tsx` оберните `RouterProvider` в `<QueryClientProvider client={queryClient}>`.
3. В `CatalogPage` замените состояние и эффект на `useQuery` с ключом `['games', apiParams]`; ошибка — с кнопкой «Повторить» (`catalog.refetch()`), счётчик и карточки — из `catalog.data`.
4. В `Header` уберите проп `count` и возьмите число игр из `useQuery` с ключом `['games', '']`: «в каталоге N игр», пока данных нет — «каталог». В `Layout` — `<Header />`.
:::

## Что получилось

Шапка: «в каталоге 40 игр». Во «Сети» при запуске два запроса `GET /api/games`: «отменён» и 200 — **один** удачный запрос на шапку и каталог вместе. (Отменённый — снова StrictMode: компоненты сняли наблюдение за записью, и Query отменил запрос, который больше никто не ждал.)

Поведение изменилось в трёх местах:

1. **Смена категории** — снова «Загружаем каталог…». Ключ новый, данных у него нет, `isPending` — `true`. В прошлом шаге на экране оставался прежний список; вернём это поведение в следующем шаге.
2. **Обратно «Все»** — список появляется **сразу**: запись `['games', '']` в кэше. Но во «Сети» — ещё один запрос: Query показал сохранённое и тут же тихо его обновил.
3. **Игра и «← Назад»** — каталог сразу, без «Загружаем», и фоновый запрос.

Почему фоновые запросы? По умолчанию данные **устаревают сразу** (`staleTime: 0`). Устаревшие данные Query показывает, но при каждом новом показе спрашивает сервер снова. Как это настроить — в следующем шаге.

## Эксперименты

1. **Повторы.** Включите «Ошибка 500» и нажмите ⟳. Около восьми секунд — «Загружаем каталог…», во «Сети» один за другим четыре ответа 500, и только потом — «Не удалось загрузить каталог. Повторить». Query **повторяет** неудачный запрос: по умолчанию три раза, с паузами 1, 2 и 4 с (каждая следующая вдвое длиннее, но не больше 30 с). Сбой на секунду покупатель не заметит. Снимите флажок и нажмите «Повторить» — каталог на месте.
2. **Нет провайдера.** Уберите `QueryClientProvider` из `main.tsx` (оставьте `RouterProvider`). Вместо магазина — «Что-то пошло не так. Ошибка в приложении…» без шапки: `useQuery` в шапке не нашёл клиента и бросил ошибку, а ошибку в макете ловит корневая граница. В консоли — `Error: No QueryClient set, use QueryClientProvider to set one`. Верните.

## Значения по умолчанию

Их стоит знать наизусть — половина вопросов «почему опять запрос?» отсюда:

| Настройка | По умолчанию | Что значит |
|---|---|---|
| `staleTime` | `0` | данные устаревают сразу после ответа |
| `gcTime` | 5 минут | запись, которую никто не показывает, удаляется через 5 минут |
| `retry` | `3` | три повтора неудачного запроса (в браузере) |
| `refetchOnMount` | `true` | новый компонент с устаревшей записью — фоновый запрос |
| `refetchOnWindowFocus` | `true` | вкладка браузера снова в фокусе — фоновый запрос устаревших записей |

## Как в настоящем проекте

- TanStack Query — стандарт для серверного состояния в React-проектах без своего фреймворка данных. Корзина, тема, черновики — клиентское состояние, им место в Zustand или контексте, не в Query.
- Шапка, каталог, страница игры спрашивают одни и те же данные через ключи — и не знают друг о друге. Это главное, что даёт кэш: компоненты не передают данные через пропсы и не договариваются, кто загружает.
- В разработке ставят [React Query Devtools](https://tanstack.com/query/latest/docs/framework/react/devtools) — панель с содержимым кэша. В превью курса её нет; что лежит в кэше, мы посмотрим в шаге «Под капотом».

::: legacy React Query 3 и 4
В старом коде: `useQuery(['games'], fetchGames)` — ключ и функция отдельными аргументами, `isLoading` в смысле «первая загрузка» (в v5 это `isPending`), `cacheTime` вместо `gcTime`, колбэки `onSuccess`/`onError` прямо у `useQuery` (в v5 их убрали). Пакет назывался `react-query`, сейчас — `@tanstack/react-query`.
:::
