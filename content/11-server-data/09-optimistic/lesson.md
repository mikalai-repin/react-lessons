У этого шага задержка — полторы секунды. Отправьте отзыв: три секунды «Отправляем…» (запрос и перезапрос списка), и только потом отзыв в списке. Покупатель не знает, дошёл ли его текст, и жмёт кнопку ещё раз.

Сервер почти всегда принимает отзыв. Так покажем его **сразу**, как будто ответ уже пришёл, а если сервер откажет — уберём. Это **оптимистичное обновление** (optimistic update): интерфейс верит в успех и откатывается при неудаче.

## Три колбэка мутации

```tsx game/ReviewForm.tsx
  // Ключ из queryOptions помнит тип данных: Review[]
  const { queryKey } = reviewsQuery(gameId);
  // Мутация — запрос, который меняет данные на сервере
  const addReview = useMutation({
    mutationFn: (review: NewReview) =>
      postReview(gameId, review),
    // До запроса: отзыв — в кэш сразу, как будто сервер уже принял
    onMutate: async (review) => {
      // Ответ идущего запроса списка затёр бы наш отзыв — отменяем
      await queryClient.cancelQueries({ queryKey });
      // Список до изменения — для отката
      const previous = queryClient.getQueryData(queryKey);
      queryClient.setQueryData(queryKey, (list = []) => [
        ...list,
        {
          ...review,
          id: -Date.now(),
          gameId: Number(gameId),
          author: 'Гость',
          date: new Date().toISOString().slice(0, 10),
        },
      ]);
      // Что вернул onMutate, получат onError и onSettled
      return { previous };
    },
    // Сервер отказал — вернуть список, каким он был
    onError: (_error, _review, result) => {
      queryClient.setQueryData(queryKey, result?.previous);
    },
    // Принят отзыв или нет — сверить список с сервером.
    // Без return: отзыв уже на экране, ждать сверки незачем
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey });
    },
  });
```

Разберём по порядку.

**`onMutate`** вызывается до `mutationFn` с теми же переменными.

1. `cancelQueries` отменяет запрос отзывов, если он сейчас в полёте (например, фоновое обновление). Иначе его ответ — без нашего отзыва — пришёл бы позже и затёр оптимистичную запись.
2. `getQueryData` — снимок кэша до изменения.
3. `setQueryData(ключ, функция)` записывает в кэш новое значение. Функция получает прежнее — как функция обновления в `useState`, — и, как там, нельзя менять массив на месте: возвращаем новый. Временный `id` — отрицательный, чтобы не совпасть с настоящими; автор и дата — те же, что поставит сервер.
4. Возвращённый объект `{ previous }` Query передаст в `onError` и `onSettled` третьим аргументом.

Все компоненты, которые показывают запись `reviewsQuery(gameId)`, перерисуются сразу — `Reviews` ничего не знает об оптимизме, он просто читает кэш.

**`onError`** — откат: кладём снимок обратно.

**`onSettled`** — вызывается после успеха и после ошибки. В обоих случаях сверяемся с сервером: при успехе получим настоящий отзыв с настоящим `id`, при ошибке — убедимся, что список верный. Здесь `invalidateQueries` **не возвращаем**: отзыв уже на экране, и держать кнопку в «Отправляем…» до конца сверки незачем.

## Тип из ключа

Ключ берём не из `gameKeys.reviews(gameId)`, а из `reviewsQuery(gameId).queryKey`. Значение то же самое, но `queryOptions` пометил этот ключ типом данных: `getQueryData` возвращает `Review[] | undefined`, а функция в `setQueryData` получает и обязана вернуть `Review[]`. Отсюда и `(list = []) =>`: записи в кэше может не быть.

::: task
1. В `ReviewForm` возьмите `queryKey` из `reviewsQuery(gameId)` (импорт `gameKeys` больше не нужен).
2. Замените `onSuccess` мутации тремя колбэками: `onMutate` (отмена, снимок, запись отзыва в кэш, `return { previous }`), `onError` (откат), `onSettled` (инвалидация без `return`).
:::

## Что получилось

Отправьте отзыв: он в списке **через долю секунды**, кнопка при этом ещё «Отправляем…». Через полторы секунды — «Спасибо за отзыв!», а во «Сети» — `POST` (201) и следом `GET` отзывов: сверка с сервером.

## Эксперименты

1. **Откат.** Включите «Ошибка 500» и отправьте отзыв «Не дойдёт». Он появился в списке, а через полторы секунды — ответ 500 — исчез, под формой — «Не удалось отправить: …», текст остался в поле. Снимите флажок.
2. **Без отката.** Уберите `onError` и повторите опыт с «Ошибкой 500». Сообщение об ошибке есть — а отзыв **висит в списке**, хотя сервер его не принял. Сверка из `onSettled` тоже получает 500, и в кэше остаются данные с «призраком». Верните `onError`.
3. **Ждать сверку.** Верните `return` в `onSettled`: `onSettled: () => queryClient.invalidateQueries({ queryKey })`. С «Ошибкой 500» отзыв исчезнет так же быстро, но сообщение об ошибке появится намного позже: мутация ждёт сверку, а запрос списка тем временем повторяется три раза — и каждый ответ идёт полторы секунды. Верните фигурные скобки.
4. **Ключ без типа.** Напишите `const queryKey = gameKeys.reviews(gameId);` (и верните импорт `gameKeys`). В консоли — ошибка с меткой «TS»: `Type 'unknown' must have a '[Symbol.iterator]()' method that returns an iterator.` — без пометки TypeScript не знает, что лежит в кэше, и `...list` не проходит. Верните.

## Как в настоящем проекте

- Оптимистичные обновления — для действий, которые почти всегда удаются и где задержка заметна: лайк, «в избранное», переименование, отметка задачи. Для оплаты или заказа — нет: там пользователь должен увидеть настоящий ответ.
- Схема «отменить → снимок → записать → откатить → сверить» — каноническая для кэша Query; её стоит знать наизусть.
- Для простых случаев есть второй способ — без записи в кэш: показывать `mutation.variables`, пока `isPending`, прямо в разметке. В React 19 то же делает хук `useOptimistic` — он появится в главе 12.
