В прошлом шаге при открытии игры консоль показала `таймер: старт`, `таймер: стоп`, `таймер: старт` — хотя компонент появился на странице один раз. Это не ошибка, а проверка, которую устраивает `<StrictMode>` из `main.tsx` (глава 1). В этом шаге кода не прибавится: разберёмся, что именно проверяет строгий режим, и посмотрим на ошибку, которую он ловит.

## Что делает строгий режим с эффектами

Когда компонент впервые появляется на странице, строгий режим в разработке после обычной настройки эффектов сразу **имитирует уход и возвращение**: вызывает очистку всех эффектов компонента и затем настраивает их снова.

```
обычно:          строгий режим (dev):
настройка        настройка
                 очистка      ← имитация ухода
                 настройка    ← и возвращения
```

Так же он поступает с колбэк-ref (шаг 2: `ref`, `очистка ref`, `ref`) и с `useImperativeHandle`. Состояние при этом не сбрасывается — это тот же компонент.

Зачем? Чтобы проверить главное свойство эффекта: **настройка, очистка и снова настройка должны давать тот же результат, что и одна настройка**. Покупатель уйдёт со страницы игры и вернётся, страницу пересоздаст `key`, зависимость изменится и вернётся обратно — во всех этих случаях эффект проходит цикл «очистка → настройка». Если очистка неполная, ошибка проявится не сразу, а в редком сценарии у пользователя. Строгий режим вызывает этот цикл сразу, при первом же запуске, чтобы вы увидели ошибку на своём экране.

В продакшен-сборке строгий режим ничего не делает: настройка выполняется один раз.

## Эксперимент: забытая очистка

Добавьте в `Countdown` лог на каждый тик и уберите очистку:

```tsx shared/Countdown.tsx
  useEffect(() => {
    if (finished) return;
    console.log('таймер: старт');
    const id = setInterval(() => {
      console.log('тик');
      setNow(Date.now());
    }, 1000);
  }, [finished]);
```

Редактор заметит, что `id` теперь не нужна: `'id' is declared but its value is never read.` Но это ошибка типов, а не сборки — приложение запустится.

Откройте «Остров сокровищ» и посмотрите в консоль:

1. Каждую секунду — **две** строки `тик`. Первый интервал никто не остановил: строгий режим вызвал «очистку», но её нет. Работают два интервала. Цифры на экране при этом идут правильно — оба интервала пишут одно и то же `Date.now()`, — поэтому ошибку легко не заметить.
2. Нажмите «← К каталогу». Страницы игры нет, а `тик` продолжается — по-прежнему два в секунду. Интервалы вызывают `setNow` у компонента, которого больше нет; React ничего не пишет в консоль, просто ничего не рисует.
3. Откройте «Остров», вернитесь в каталог, откройте снова. Теперь каждую секунду **шесть** `тик`: каждый заход добавил по два интервала, и ни один не остановлен.

Без строгого режима ошибка та же, только медленнее: один лишний интервал на каждый заход на страницу. Её бы нашли через месяц, по жалобе «магазин тормозит, если долго листать игры». Строгий режим показал её при первом запуске.

Верните очистку `return () => clearInterval(id);` — и снова: одна строка `тик` в секунду, после ухода со страницы — ни одной.

## Эксперимент: флажок вместо очистки

Частая реакция на двойной запуск — «запретить» его флажком в ссылке:

```tsx shared/Countdown.tsx
  const started = useRef(false);

  useEffect(() => {
    if (finished || started.current) return;
    started.current = true;
    console.log('таймер: старт');
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => {
      console.log('таймер: стоп');
      clearInterval(id);
    };
  }, [finished]);
```

Откройте «Остров»: `таймер: старт`, `таймер: стоп` — и таймер **стоит** на месте. Строгий режим вызвал очистку (интервал остановлен), а повторную настройку не пустил флажок: состояние и ссылки при имитации не сбрасываются. Флажок не чинит эффект, а прячет проверку — и ломает его. Уберите флажок.

Правильный ответ на двойной запуск — не «как его избежать», а «как написать очистку, чтобы повторная настройка ничего не ломала».

## Какой бывает очистка

| Настройка | Очистка |
|---|---|
| `setInterval`, `setTimeout` | `clearInterval`, `clearTimeout` |
| `addEventListener` | `removeEventListener` с той же функцией |
| `observer.observe(el)` | `observer.disconnect()` |
| подключение к серверу (`WebSocket`) | `socket.close()` |
| запрос `fetch` | `controller.abort()` (или игнорировать ответ) |
| виджет сторонней библиотеки | его метод `destroy()` |

С запросами вы уже встречались. В демо-магазине шага 1.1 во вкладке «Сеть» первый запрос каталога был «отменён», а второй — успешен. Это строгий режим: компонент каталога «ушёл» сразу после запуска, библиотека запросов отменила ненужный запрос и отправила его снова, когда компонент «вернулся». В продакшене запрос был бы один.

## Как в настоящем проекте

- Не убирайте `<StrictMode>`, чтобы избавиться от двойного запуска: вместе с ним уйдёт проверка, а ошибка останется.
- Видите в разработке что-то дважды — два запроса, два подключения, две записи аналитики — сначала проверьте очистку. Если очистка правильная, двойной запуск безвреден, а в продакшене его нет.
- Бывает действие, которое не нужно повторять **никогда** за всё время работы приложения: например, один раз инициализировать SDK при загрузке. Его выносят из компонентов на уровень модуля, в `main.tsx`, до `root.render`.
